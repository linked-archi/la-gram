# Requirements: la-gram

## Introduction

la-gram is an RDF-first architecture modeller: the model lives in an RDF store
(Oxigraph) and every other representation — the diagram canvas, the model tree,
catalog and matrix views, files, the collaboration document — is a projection of
it. Metamodels are published Linked.Archi assets (`meta.linked.archi`) loaded at
runtime; the diagram canvas is diagram-js; real-time collaboration is Yjs over
Hocuspocus. It runs in the browser and as an Electron desktop app.

These requirements are adapted from the `la-modeller-excalidraw` specification
(`tools/modellers/excalidraw-linked-archi-yjs-demo/.agents/specs/la-modeller-excalidraw/`),
which is the reference for behaviour; requirement numbers 1–11 match it so the
two can be compared line by line. Where la-gram deliberately differs, the
criterion says so. Requirements 12–22 are specific to la-gram. The broader,
implementation-independent tool specification is `docs/linked-archi-tool-spec.md`.

## Glossary

- **Model** — an `arch:Model`: elements, relationships and views. At runtime the
  store's default graph; at rest a file.
- **Element / Relationship** — model concepts. A relationship is an
  `arch:QualifiedRelationship` subclass instance with `arch:source`/`arch:target`
  *and* the unqualified triple its class maps to (`arch:unqualifiedForm`), which
  the instance `rdf:reifies` (RDF 1.2).
- **View** — an `arch:View` (`arch:Diagram`, `arch:Catalog` or `arch:Matrix`)
  presenting a subset of the model; conforms to a viewpoint.
- **Placement / geometry** — `arch-vis:ArchNode` (an element in a view) and
  `arch-vis:Link` (a relationship in a view), with bounds and routes.
- **Canvas** — the diagram-js surface showing one diagram view. Not persisted.
- **Metamodel** — an `arch:Metamodel` manifest and the documents it names
  (ontology, taxonomy, notation, shapes, viewpoints, presentation contexts).

### Requirement 1: Metamodel Loading & Discovery

**User Story:** As an enterprise architect, I want the tool to load metamodels from `meta.linked.archi` (or anywhere else), and to let me add my own — so that I can work with published metamodels, custom extensions or third-party ontologies.

#### Acceptance Criteria

1. On startup, load the default metamodel — ArchiMate 4.0 (`https://meta.linked.archi/archimate4/metamodel#ArchiMate4`) — or the metamodels named by `?metamodel=` (repeatable, comma-separated)
2. Offer every published metamodel in a selector so the user can add one, or switch to it (replacing the others); unloading one takes every document it loaded with it — those its manifest names and those they import — but the core's and any another loaded metamodel uses
   - *la-gram:* the selector lists `meta.linked.archi`'s DCAT catalogue (`https://meta.linked.archi/catalog`): every metamodel manifest it themes `languages`, `frameworks`, `extensions` or `core`, under those sections, by label (the examples' metamodels are not offered), A copy ships with the app, so the list is complete offline; unless offline, the published catalogue replaces it when it arrives, so a newly published metamodel is offered without a new la-gram (`src/metamodel-manager/catalogue.ts`)
3. Parse the manifest and discover all linked resources via `owl:imports` and `arch:*` properties (`arch:modelConcepts`, `arch:conceptClassification`, `arch:notationSet`, `arch:formalRules`, `arch:architectureViewpoints`, `arch:presentationContextScheme`, …)
4. Load discovered resources in parallel (one level of the reference graph at a time) with `Accept: text/turtle`
5. Multi-value Accept headers with quality parameters must not be sent (the server returns 404)
6. In addition to the catalogue, the user can:
   - Provide the IRI of a **complete metamodel** (any `arch:Metamodel` subject or manifest); all its assets are discovered and loaded
   - Upload a **complete metamodel** (a manifest file); its other documents resolve through the normal sources
   - Upload **individual semantic assets** (an ontology, a shapes file, a viewpoints file), added to the loaded pool
7. Switching metamodels updates the palette, relationship validity and validation shapes; model content that does not match the new metamodel stays, is shown as *unclassified*, and is flagged by validation — never removed
8. ~~No hardcoded/embedded ontology~~ — *la-gram deviates deliberately:* ArchiMate 4.0 and 3.2 (and the core ontologies and shapes) ship with the app so it starts and edits offline, and so ArchiMate Exchange files import without network. Every other metamodel comes from the network or an upload. Source order is configurable: `?assets=bundled-first` (default in the browser), `remote-first`, or `offline`
9. Track asset loading status per document (loaded / already-loaded / skipped / unavailable / error, origin, triple count) and show it ("Show loaded assets")
   - Bundled snapshots are refreshed explicitly before building. `sync-assets` uses `https://meta.linked.archi/` by default, with its published catalogue; `--meta <path>` or `LINKED_ARCHI_META` explicitly selects a local checkout, and `--online` overrides the environment selection. Local mode uses the checkout's publishing scripts and its last generated catalogue, whose freshness must be established separately. `--check` is read-only. Online request failures fail the sync without local fallback or partial snapshot changes; required downloads are staged before writing. Metamodels listed only in the catalogue, including LeanIX, resolve remotely, and already-loaded documents remain in the session until la-gram is reopened. Every rebuilt asset copy matches the current snapshot, including removal of files no longer in it.
10. Cold-start to interactive ≤ 3 seconds (measured: ≈ 1.2 s with the bundled ArchiMate 4.0)
11. Multiple metamodels can be loaded simultaneously; palette, validity rules and validation use the union
12. **Basic, the generic language** — meta.linked.archi's Basic, bundled so it works offline: added to a language or alone, it offers its element types (Node, SpecialNode, GroupNode) and its relationship types, of which **Connection** relates any two elements — of Basic, of another language, or across them — and ranks last among a language's relationships (like Association, it never makes a choice ambiguous); Association and Aggregation keep Basic's restrictions. The first-loaded language's grouping stays the default. Unloading it keeps the core ontology every model depends on. A core class (`arch:Element`, `arch:QualifiedRelationship`) is never a palette type; Basic's notation draws one that a model contains
   - *la-gram:* `meta.linked.archi` publishes no core manifest, so la-gram bundles one (`assets/core/core-metamodel.ttl`) with a small classification (`assets/core/core-tax.ttl`, `https://meta.linked.archi/core/tax#`) naming the two generic concepts — the palette offers a core class only when this classification names it
12. Documents the editor cannot use (derivation rules, deliverable templates, reference models, the framework document) are recorded as *skipped* rather than fetched. Reference data is loaded: it names the values properties take. Question sets (`arch:hasQuestionSet`, and the core set) are loaded: their model questions are offered in the workbench
13. **Architecture Decisions, bundled** — meta.linked.archi's decision extension (`admm:ArchitectureDecisions`), bundled so it works offline and is in the Metamodels menu under *Extensions*: added beside a language, it offers its element types in two sections — *Decision Record* (Issue, Decision, Option) and *Forces* (Force, the kinds of Requirement and Constraint, Principle, Policy, Trend, Personal Preference) — and twenty-nine relationship types in six categories (*Record Links*, *Change Links*, *Force Links*, *Decision Map Links*, *Stakeholder Links*, *Issue and Design Links*) — those whose predicate is `owl:SymmetricProperty` (*Conflicts With*, *Opposing Force*, *Complementary Force*) a plain line, each drawing one link of the decision vocabulary: drawing *Modifies* from an Option to an element writes `ad:modifiesConcept` and its relationship resource. A kind of relationship with no qualified property of its own uses its nearest superclass's (*Supporting Influence*: `ad:hasInfluence`). It has no notation: its elements are drawn by the fallback
14. **Architecture Processes, bundled** — meta.linked.archi's processes extension (`apmm:ArchitectureProcesses`), bundled as the decision one is, so it works offline and is in the Metamodels menu under *Extensions*: added beside a language, it offers its element types in three sections — *Process Structure* (Architecture Process, Process Activity, Process Task, Process Milestone), *Deliverables* (Process Deliverable, Information Item) and *Roles* (Process Role) — and thirteen relationship types in four categories (*Structure Links*, *Flow Links*, *Responsibility Links*, *Governance Links*), *Related Process* a plain line. LeanIX and EA on a Page, which import its vocabulary, load it from the bundle too

### Requirement 2: Palette Generation & Viewpoint Filtering

**User Story:** As a modeler, I want a palette derived from the loaded metamodel's ontology, grouped by its taxonomy and filtered by the view's viewpoint — so that the tool adapts to any metamodel without code changes.

#### Acceptance Criteria

1. Dual classification: the **SKOS taxonomy** decides which concepts appear and how they are grouped; the **OWL ontology** provides the class instantiated. Linked by shared IRI or `rdfs:seeAlso`
2. Only concrete (instantiable) element types are offered; `arch:isAbstractClass true` is excluded
3. Labels: `skos:prefLabel` → `rdfs:label` → local name
4. Definitions: `skos:definition` → `rdfs:comment`
5. Grouping derives from the taxonomy scoped by `arch:conceptClassification`, navigating `skos:narrower` and inverse `skos:broader`; group and axis roles are detected structurally, and a concept the primary metamodel's palette grouping (`arch:paletteGrouping`) names is an axis whatever its shape; an element type is an ontology class — listed itself, or by a concept with nothing under it that stands for it (`rdfs:seeAlso`, or the same local name), or named with others by such a concept's `rdfs:seeAlso`, which is then their group, as is each sibling written so (DoDAF's and UAF's viewpoints, the ML extension's phases) — a class with a well-known relationship name (Realization, Flow…) is a relationship type only where its superclasses do not make it an element; so a concept with nothing under it and no class behind it is no element type, and does not stop the concept above it being an axis; with no classification loaded — or none that classifies a class: core's question stages are a scheme too — the palette lists the ontology's element classes grouped by a guess from their names, and says so ("No classification loaded — types grouped by name")
6. Several classification axes are preserved; a "Group by" selector switches between them. The default is the first axis the primary metamodel's palette grouping names (`arch:paletteGrouping`), else the first by name; no metamodel-specific special cases, and no axis preferred for its label
7. Relationship-only axes are not offered for element grouping
8. The palette is filtered by the **open view's** viewpoint (`arch:includesConcept`); a viewpoint naming a class includes its subclasses (`rdfs:subClassOf*`), as the published viewpoint conformance shapes read it. What it names is an element type or a relationship type by its class (a subclass of `arch:QualifiedRelationship` is a relationship type). A viewpoint naming element types and no relationship type — every ArchiMate 4.0 viewpoint — offers every relationship type: a relationship the metamodel permits between its elements is in the viewpoint, and connect still offers only what a pair permits. A viewpoint naming nothing offers nothing
9. Viewpoint filtering is non-destructive: elements outside the viewpoint stay on the canvas, greyed out, still editable
10. With no viewpoint, all concepts are offered
11. With several metamodels loaded, the palette shows the union: the types the first one's grouping does not classify keep their groups under their own metamodel's classification, as sections after its own (Basic's *Elements*, the decision extension's *Decision Record* and *Forces* beside ArchiMate's domains)
12. Visual notation comes from the metamodel's `arch:notationSet` (`arch-vis:NotationSet` / `arch-vis:VisualNotation`)
13. Each `arch-vis:VisualNotation` provides shape, fill, line, icon, icon placement, rendering mode and default size
14. Three rendering modes: `ShapeWithBadge`, `IconCentric`, `ShapeOnly`
15. **Presentation contexts** (`arch:presentationContextScheme`) are offered in the toolbar; the chosen context's `arch:usesNotationSet` restyles palette and canvas. The sets the contexts name are loaded with the metamodel, so an alternative set needs no other reference; the manifest's `arch:notationSet` stays the default
16. Notation lookup, the same for palette and canvas. For a class C, the active set A is the set that the active presentation context names with `arch:usesNotationSet`, or else the primary metamodel's `arch:notationSet`. The fallback layers F are the default sets (`arch:notationSet`) of all loaded metamodels except A itself, in load order, then the core notation's (`https://meta.linked.archi/core-notation#`), which no manifest names and which is never the active set: it draws the core's own relationship types (Req 4.21). F includes the default set of A's own metamodel when a presentation context picked an alternative set. (1) A descriptor in A for C. (2) A descriptor for C in F, the first match in load order. (3) C's own `arch:prefVisNotation`. (4) A descriptor for the nearest superclass of C that has one in A or F. The walk goes breadth-first over `rdfs:subClassOf`: by distance first, and superclasses at the same distance in IRI order. It stops at `arch:Element` and `arch:QualifiedRelationship`. For each superclass, A is checked first, then F in load order. (5) Built-in defaults. Elements: a rectangle with a white fill and a black line. Relationships: a solid black line. Anything published for the class itself beats anything inherited; among inherited descriptors the nearest ancestor wins; the active set only breaks ties. Relationships are drawn black unless a descriptor states a colour; they differ by line style and arrowhead
17. **Relationship ends** are drawn from the published marker symbols: each `arch-vis:Decoration` names its SVG with `arch-vis:decorSymbol`, placed as the vocabulary describes (pointing in +x, the connector meeting the middle of its viewBox's right edge, mirrored at a source end, `currentColor` taking the line's colour). The core-vis markers ship with the app; built-in geometry draws a decoration only while its symbol loads, or when none is published or it cannot be loaded
18. **Element shapes** are drawn as the notation describes them, so the canvas matches the published pictures. The eight core shapes (`Rectangle`, `RoundedRectangle`, `Octagon`, `Ellipse`, `Circle`, `Hexagon`, `Diamond`, `Parallelogram`) are drawn natively. Any other shape is declared by the notation that uses it — ArchiMate's 3D box, banded, tabbed and wavy rectangles, cloud and folder; EDGY's arrow and pill; C4's person, mobile device, web browser and cylinder — with a core fallback and its geometry as path templates (`arch-vis:outlinePath`, `detailPath`, `contentBox`, `labelBox`, `shapeVariables`), and drawn from those: no notation needs code. A shape whose templates cannot be evaluated, or that has none, is drawn as its fallback; one with neither, as a rectangle. Only core-vis's own names are core shapes. Inner lines (a template's `detailPath`) are drawn but are not outline: connections dock against the outline. The badge and the label sit in the content box (below a band, on a 3D box's front face, above a wave); the label in the label box when there is one (a folder's tab), on as many lines as it is tall enough for. `arch-vis:borderStyle` dashes or dots the outline (ArchiMate's grouping). The label takes `arch-vis:fontColor`, else the line colour (under an IconCentric icon, else black). The badge is the published glyph as it is: its lines opaque, transparent where the element's fill shows through. A shape too small to hold one line of its label (a junction's 15 px circle) draws no badge, and its name — if it has one of its own, not its type's — under it, where it is also typed when renamed
19. **A look per kind, a set per audience.** A kind of element with a look of its own is a subclass with a descriptor of its own (C4: `c4:Database` ⊂ `c4:Container`, drawn as a cylinder); a different look for a different audience is a notation set chosen by a presentation context (Req 2.15). Notation data has no conditions on element values
20. **Relationship icons.** A relationship type is shown with the icon its notation publishes (`arch:prefVisNotation`), else with one drawn from its notation — a short line in its line style and colour, with its end decorations, as the canvas draws it (ArchiMate publishes none for its relationships) — or, with no notation, a plain line: in the palette and in every menu that offers relationship types (append, nest, change type, connect two). A named icon that does not load is replaced by the drawn one
21. **Which type an entry is.** Each palette entry's tooltip gives its name and prefixed IRI (`Serving — am4:Serving`); where loaded languages share a name (ArchiMate 4.0 and 3.2, Basic's Aggregation), each such entry carries its prefix (`am4`, `am`, `basic`) beside the name. The search matches the prefixed name too (`basic:` lists one language's types)
22. **Relationships first.** The palette lists the relationship types above the element groups, under the search box and the "Group by" selector. Their section is folded at first, its count beside its header, and unfolds and folds by it, as a group does; a search opens a folded section or group, so a match is never hidden. Where the taxonomy classifies relationship types (an axis whose groups list them — ArchiMate's Relationship — by the class or by a concept that stands for it, `rdfs:seeAlso`: LeanIX's, BPMN's), each loaded metamodel's types take their categories from the dimension that lists them (of several listing one type, the one that lists the most), the dimension that lists the most first; a group under no dimension (LeanIX's Relationship Type) gives categories beside one that is, the section holds a group for each category, in the order of that axis's thesaurus array (ArchiMate's `:RelationshipOrder`: Structural, Dependency, Dynamic, Other Relationship), each folding by its header with its count; a kind of relationship the taxonomy does not list (Read Access) is in its nearest superclass's category; within a category the types follow the thesaurus array under it — strongest first, as the specification lists them (ArchiMate's Composition, Aggregation, Assignment, Realization; Serving, Access, Influence, Association; Triggering, Flow) — a kind just after the relationship it is a kind of, then by name. With no such axis, one list by name
23. **Sections in the metamodel's order.** The element sections follow the order of the axis they come from — its thesaurus array's, the ISO 25964 array whose `iso-thes:superOrdinate` is the axis (`skos:memberList`); a nested group by the group it is under — then their names, *Other* last; a group the array does not list after those it lists. Under an axis the palette grouping names, a type the axis does not classify goes in the section of its group under the next axis it names (ArchiMate 3.2's motivation elements, of no layer, in *Motivation*), after the axis's own sections; and the types within a section follow the thesaurus array under their own group, where it has one (ArchiMate 4.0's Common Domain: Process, Function, Service, Event, Role, Collaboration, Path, Grouping, Location), then their groups' order under the other axes it names, then their names (in a domain or layer: structure, active and passive, then behaviour, then composite). A type no axis it names classifies goes in the section of a group under no axis and no other group that lists it — ArchiMate's *Junction*, a top concept of its own — after those sections, else in *Other*; such a group is no *Group by* choice. An axis the palette grouping does not name groups alone, its types by name
24. **A metamodel that is incomplete, said.** Every element type a loaded ontology defines is offered: one that no classification names — its metamodel names none, beside a metamodel that does, or its classification leaves it out — is listed in a section **Other**, after the others. The palette says of each loaded metamodel what it leaves out, by its name and with its numbers: that it *defines no element or relationship types* — its documents hold concepts and no classes, or classes none of which is a subclass of `arch:Element` or `arch:QualifiedRelationship` — so nothing of it can be drawn; that it *names no classification* (`arch:conceptClassification`), its element types listed under *Other* (or, where no loaded metamodel has one, grouped by name); that its classification names so many of its element types, the others listed under *Other*; that so many of its relationship types are in no category. that its classification *names none* of them, where they are grouped by name. A type is a metamodel's — offered, and counted — when one of the documents it takes its types from declares it: those its manifest names as its concepts (`arch:modelConcepts`) and what they import; a document only its shapes, mappings or viewpoints import (another version's ontology: LeanIX v3 beside v4, TOGAF 9.2 beside 10) is loaded for validation and gives no types. The core's are no one's, and a kind of view (`arch:View`: BPMN's diagram) is no element type. *Details…* in the notice opens *Show loaded assets…*, which says the same under the metamodel, with the types by name; **✕** closes a notice, which stays closed in this browser (`la-gram:palette-notices-closed`) while it would read the same and is shown again when it would not
25. **A relationship type no notation describes** is drawn as a solid line with an open arrowhead at its target — it leads from its source to its target, and the links of a metamodel that publishes no notation (a decision's, a process's, an evaluation's) read by their direction — and its palette and menu icon the same. One whose direct predicate is symmetric (`owl:SymmetricProperty`: a decision that conflicts with another) has no direction and is a plain line. A type its notation describes is drawn as that says — the core's by the core notation: Association, Has Part and Refines with the lines these rules would give them, Depends On dashed (Req 4.21)
26. **Element icons.** An element type is shown with the icon its notation publishes (`arch:prefVisNotation`, else its badge glyph `arch-vis:iconSymbol`), else with its figure drawn from its notation — its shape, a notation's own shape with its inner lines, in its fill and line colours, as the canvas draws an element of that type — or, with no notation, the canvas's default figure: in the palette and in every menu that offers element types (append, nest, change type). A named icon that does not load is replaced by the drawn figure

### Requirement 3: Element Creation & Properties

**User Story:** As a modeler, I want to create elements from the palette, name them, and manage their properties, so that each element carries full semantic metadata.

#### Acceptance Criteria

1. Dragging a palette entry onto the canvas creates the element at the drop point; clicking an entry arms click-to-place
2. Each element has a stable IRI (UUID-based, minted at creation, never changed), its class, a language-tagged `skos:prefLabel`, and `arch:inModel`; it is placed in the open view as an `arch-vis:ArchNode`
3. The label is editable in the property panel — and on the canvas, in the element's box: double-click it (or select it and press F2), type (the name starts selected, so typing replaces it), Enter or a click elsewhere keeps it, Esc drops it; one line, and never empty. It is the `skos:prefLabel` in the language shown (other languages' names are kept), an undoable canvas step; the canvas, the tree and the property panel follow
4. Selecting an element (canvas or tree) shows it in the property panel (the Properties tab under the canvas): kind, type, IRI, properties, relationships, the views it appears in. Fields are named in words and links by the name of what they link to, so the panel reads without knowing RDF; clicking a field's name or a link shows the IRIs behind it. A link's value is added by picking a concept of the model by name (or typing an address or text)
5. Properties are persisted with the element and included in every export
6. Properties are added by picking or typing a property and a value; values can be removed (not the type, not the name). The picker offers what applies to the concept's type (by `rdfs:domain` / SHACL), what the model already uses, documentation properties, and — folded — the rest; never diagram geometry, notation styling, metamodel-authoring terms or a property its vocabulary deprecates (`owl:deprecated`). Entries show the name first, the prefixed IRI smaller. A link's value is picked from the model's concepts and views by name, with a switch for each kind beside the search — *Elements*, *Relationships*, *Views*, all on at first — or typed. Any property can be typed: a plain name (a new property in the model's namespace, `m:owner`), a prefixed name, or an IRI. The panel lists, in order: ID (the IRI), type, `inModel`, `prefLabel`, `skos:definition` — the name and the definition always, empty until filled in (emptying the definition removes it; the name cannot be emptied) — then — in the panel's own *Properties* tab, with the add field — every other property by label. A link (an object property) is offered by its `rdfs:domain` or `arch:domainIncludes` when that is more particular than `arch:Element` — one from any element, core's notation and authoring links among them, can be typed — unless a loaded relationship class draws it: its `arch:unqualifiedForm`, the declared inverse of one (`owl:inverseOf`), or a qualified predicate are made on the canvas, not typed here. `arch:inView` is not listed: the views are in the toolbar and under "Appears in views". A property whose SHACL shape lists its values (`sh:in`) is a choice of them, for adding and editing, each labelled by its name in the loaded data (a metamodel's reference data: "Serverless Function") else its local name in words — a link too, which is then offered as an attribute (Backstage's `bs:lifecycleState`); a boolean is a checkbox (true/false when adding); an added value takes the shape's datatype. An edit replaces the value edited and no other (the name in another language stays); with a view open, each edit, addition and removal is an undoable step, and undo puts the canvas back too
7. Deleting: **Delete from View** (the canvas default — Delete key, pad ×) removes the placement only; **Delete from Model** (pad ✖, tree menu) removes the element everywhere after a confirmation listing the views it appears in
8. Delete from Model removes every relationship connected to the element, in every view
9. Edit latency ≤ 16 ms per command
10. **About ‹type›** — a section of the left panel, under the model tree, tells what the loaded metamodels say about the selected concept's type (for a view, its viewpoint) — or about a type picked in the palette, until something is selected: from the ontology its definition, other names, guidance (`skos:scopeNote`), typical ends and unqualified form of a relationship, a viewpoint's concepts, stakeholders, concerns and purposes, the classes it specializes (with their definitions), what changed, and its source in the specification; from the taxonomy where it is classified — the path under each axis ("Domain › Business Domain"), the group's definition and notes, and the other types in the group. The section folds to its header ("About Business Actor") and is resized by its top edge — its height and folding remembered; its parts fold too, and which are open is remembered; any type or concept it names opens its own page, with a way back; a new selection shows its own type again. With nothing selected, or a type the metamodels say nothing about, it says so. Under the type's name, its IRI as a prefixed name (`am4:Serving`, from the loaded vocabularies' prefixes); a click shows the whole IRI, with Copy. A palette entry under the pointer is shown there after a short pause — none while the pointer sweeps across the palette — and what was shown comes back when it leaves
11. **Change an element's type** — an *IRI* button beside the editable direct *Type* shows or hides its full current IRI, selectable for copying, without opening the chooser or changing the element; the button works by mouse and keyboard and shows the new type after a type change. Change the type from the property panel, where an element's *Type* is a choice of every element type of the loaded metamodels, searched by name (grouped as in the palette; types that share a name show their IRIs, and the list's "Show IRIs" shows every one; also for an element not in the open view), or from the right-click menu's "Change type…", a searchable menu of the same types with the current one marked, where types that share a name show their IRIs and "Show IRIs" (the same setting) shows every one. The element keeps its IRI, name, properties and placement in every view; a name that was still the old type's default becomes the new type's. Relationships the new type is not permitted in are named first (e.g. "Assignment → Cashier") and, if the user goes ahead, kept — validation flags them; nothing is deleted. One undoable step
12. **Nesting** — an element is drawn inside another by dropping or moving it there (an element too small to hold a name, a junction, holds nothing); the placement is stored as `arch-vis:inNode` on its node, bounds staying in the diagram's coordinates. What is inside moves with its container, which grows to hold it, and the container's name moves to its top — on at most two lines that what is inside never covers: something dropped or moved there makes the container grow above it — and is there whenever the view is drawn, opened again or changed by a collaborator; emptied, the name goes back to the middle. A drop into an element offers the relationships the nesting may stand for — those whose notation lets nesting draw them, with the dropped element as the end drawn inside (`arch-vis:nestedEnd`), and the metamodel permits between the two (ArchiMate: composition, aggregation, assignment, realization, access, specialization; C4: containment, deployment; between elements no loaded language relates, the core's has part and refines, Req 4.21) — or None; the one picked is created in the model and not drawn as a line. Nothing is offered when the model already relates them so. What the nesting stands for — the relationship picked, and any the model already has between the two that nesting may draw, inner element the end inside — is the view's (`arch:inView`) and shown by the nesting. No line runs between a nested element and its container: every line between the two, of any type and either way, goes when the element is nested and stays the view's. Taken out of the container, the relationships the view showed by the nesting are drawn as lines again — those the view recorded, and those the nesting stood for though nothing recorded it (a model opened nested: of a type nesting may draw, the element the end drawn inside) — never others the model has between the two. In the same undoable step as the move. One undoable step each
13. **Figures** — drawing with no model element behind it, from the canvas toolbar's *Shapes* row (closed by default, remembered per browser): a **group** (a box with its name in a tab), a **note** (a sticky note, its text from the top left) and the core-vis **shapes** (rectangle, rounded rectangle, ellipse, circle, diamond, hexagon, octagon, parallelogram). Pressed and dragged onto the canvas, or clicked and placed; stored in the view as core-vis nodes — a group or a shape an `arch-vis:ContainerNode` (a shape's `arch-vis:style` giving its `arch-vis:shapeType`), a note an `arch-vis:LabelNode` no element's label points at — their text their `skos:prefLabel`. Moved, resized, renamed on the canvas, deleted, copied with their view; a group or a shape holds elements and figures as an element does (Req 3.12), a note nothing; no relationship ends on one. ### Requirement 4: Relationship Creation & Integrity

**User Story:** As a modeler, I want to create relationships the metamodel allows, with the tool keeping the model structurally sound.

#### Acceptance Criteria

1. Selecting an element shows diagram-js's context pad with Connect and Append. While connecting from the pad or toolbar, a blue preview line follows the pointer across empty canvas, including after leaving a target; over a target it docks to the target's outline. Completing or cancelling the gesture removes the preview
2. Connect (pad or toolbar tool), Append and "change type" offer only the relationship types the metamodel permits for the pair, best first: where the metamodel publishes relationship shapes (ArchiMate 4.0 and 3.2 — the relationship matrix), exactly the pairs they list, a shape on a superclass applying to its subclasses (Composition ⊂ Aggregation); elsewhere the `arch:domainIncludes`/`arch:rangeIncludes` hints (closure-aware); within what is permitted, three groups — those the tables let a modeller draw directly (the tables' upper case — ArchiMate 4.0 and 3.2 — or where they say nothing), then those permitted only as the conclusion of a derivation, then the fallbacks, Association and the core's generic relationship, unless an order of proposal scoped to the pair lists one (ArchiMate: Association to a Meaning or a Value) — and within each group the place the most specific order of proposal the metamodel names (`arch:relationshipProposalOrder`, read from the metamodel's own documents only, so a model file adds none) gives it: an order naming both elements before one naming one, a subclass's before its superclass's, before the general order (ArchiMate: between two behaviour elements Triggering and Flow first, then Composition and Aggregation; from a process to a service Realization; elsewhere the strongest first, between two application components Composition, then Aggregation); what no order lists after, a relationship whose `arch:domainIncludes`/`arch:rangeIncludes` hints describe the pair first. What the language's metamodel figures draw (the relationship tables' `drawnBy`) does not move a relationship. A connect with no type chosen draws the best-ranked type and opens the relationship-type menu on the new line — every permitted type, best first, as change type lists them — when the pair permits more than one specific type (Association aside); picking one changes it, in the drawing's own undo step — one undo takes the line away, one redo draws it with the type picked — and Escape keeps it. The menus say, in words, "drawn in the metamodel", "only by derivation", "always permitted"
3. Dropping the connection on a target creates the relationship with the best-ranked type; the pad's "change type" menu lists the alternatives
4. Append ("+" on the pad) lists the element types a relationship is permitted to, with their icons, and creates the new element *and* the relationship to it, as one undo step. When one specific relationship is permitted (Association aside, directed or not) it is created directly; when several are, a second step asks which, Association last. A drag from the menu takes the best-ranked one. The menu has two tabs: **New element** (the above, grouped by the palette's categories — the source's own type first, then its own category, then the others in the palette's order; within a category the types most like the source first — the most superclasses in common — then the palette's order, a type only Association reaches last: after an ArchiMate 4.0 process, a process, a function, a service, an event, then the Business, Application and Technology Domains) and **Existing relationships** (n) — the relationships the element already has in the model, those whose other end is not in the view first; a click brings the other end into the view beside the element (right for outgoing, left for incoming, at a free spot) with the relationship drawn, a drag places it where dropped; nothing new is created in the model
5. Relationship types are in the palette; picking one arms the connect tool with that type, required: a pair the metamodel does not permit it for cannot be connected, and releasing on one says which relationships the pair permits (never a different type in its place)
6. Connections are bound to their elements and follow them. Moving, resizing or reattaching an element moves only the ends: the bends the user placed stay (one an element is resized over goes, being inside it), and each end docks on the element's outline. An end dropped beside its element, or in the empty corner of its box, docks on the outline all the same. A new line between two elements runs from centre to centre, cropped at their outlines, wherever the gesture pressed and let go; an end on a relationship keeps its point, as does a line from an element to itself. A right-angled line — as Arrange view draws them — stays right-angled when an element moves or is resized: the bend next to the moved end follows it, the other bends stay; where a bend would fall inside an element, the line is routed again at right angles; an arranged straight line (its ends on the outlines, not aimed at the centres) turns right-angled when an element leaves its axis
7. Each relationship is a qualified resource (stable IRI, class type, `arch:source`, `arch:target`, `arch:inModel`) *and* the unqualified triple, which the resource `rdf:reifies` (RDF 1.2, kept in step through retype and reconnect, added on load where missing); it is drawn as an `arch-vis:Link` with its route. A resource that reifies a triple the model does not assert, with no qualified predicate leading to it, is a proposition, not a relationship of the model: loading gives it no qualified predicate, `arch:inModel` or link. A derivation the model does not state — a valid one, or a potential one no qualified predicate leads to — gets no `arch:inModel` and no automatic link, is listed apart in the explorer by certainty with its rule, is drawn faded with a badge (D, P) when added to a view, and shows its rule and premises in the properties panel; *Confirm* states a potential one (its triple, its qualified predicate, `arch:inModel`) as one undoable step
8. Relationships are first-class: selectable, with properties, in the tree, in the property panel
9. Relationships support custom properties like elements
10. Connections cannot exist unattached: an end can be reattached only to an element, or a relationship, the metamodel permits for it; let go on empty canvas, it stays where it was
11. Changing a relationship's type keeps its IRI and properties (retyped in place), undoably
12. Deletion as for elements: from the view by default, from the model on request
13. `domainIncludes`/`rangeIncludes` are indicative; SHACL decides validity — the relationship shapes both for what is offered and in validation, so an offered relationship never fails validation
14. A kind of relationship is a subclass of its relationship class, sharing its predicate (ArchiMate's `ReadAccess`, `WriteAccess`, `ReadWriteAccess` and `DirectedAssociation`): it is offered wherever its class is, drawn with its own ends, and changed by changing the relationship's type. A bare triple with the shared predicate is the most general class
15. Two selected elements: the context pad offers "Connect these two…", a menu of the relationships they may have in either direction, ranked as connect ranks them (derived-only ones marked); the pick creates the relationship, as one undo step
16. **A relationship whose source or target is a relationship** (the core allows any `arch:ModelConcept` at either end: an association to a flow, a composition into a relationship) is drawn to that relationship's line. Dropped on the line, its end docks on it, and stays at the same place along it when either moves, when the line is bent or re-routed, and through undo. In a view its `arch-vis:Link` ends on the other relationship's Link (core-vis 0.6): it is drawn after it, removed from the view with it, and deleted from the model with it. Placing an element draws the relationships ending on those it brings in; the ArchiMate exchange import draws a connection ending on a connection
17. **A relationship's name** (its `skos:prefLabel`) is shown at the middle of its line when the canvas toolbar's *Relationship names* switch is on — off by default, remembered per browser — and only for a relationship that has a name of its own: one without shows nothing, not its type. Wrapped at an element's width to at most three lines; the line stops at it; on a derived line, under the badge and faded with the line. It is named on the canvas as an element is (Req 3.3): double-click its line or its name, or select it and press F2 — the box opens at the middle of the line, holding the name (empty for one without), whether names are shown or not; Enter or a click elsewhere keeps it, Esc drops it; emptied, the name is removed. One undoable step; the canvas, the tree and the property panel follow, and the line follows a rename made elsewhere. A derivation the model does not state is not named (confirm it first). The name is the model's; where it is drawn is the view's (4.18)
18. **Moving a relationship's name**: a name shown on its line is dragged off the middle — a press on the name drags the name, not the line (elsewhere on the line, the line's own handles as before); Esc drops the drag. The view keeps where it was put: an `arch-vis:LabelNode` hung on the relationship's `arch-vis:Link` with `arch-vis:label`, in the view (`arch-vis:view`), with its bounds in the diagram's coordinates — read back when the view is opened, removed and restored with its link, copied with its view, and following a collaborator's move. The name keeps its place relative to the middle of the line as the line is re-routed or its ends move, its bounds written with the route in the same undoable step. Right-click › *Move name back to its place* drops the label node: the name is back where its look anchors it (Req 3.15) — the middle unless it says an end. Each an undoable step; not while a collaborator holds the line
19. **Lines above shapes**: every relationship's line, with its name, is drawn above every element — nested ones included — as ArchiMate tools draw them, whatever was created, moved, nested or taken out since the view was opened, by the user or a collaborator, and after undo
20. **Drawing a relationship the model already has**: a line drawn from one element to another, of a type the model already relates them by in that direction and that this view does not draw between those two placements, asks first — *Use the existing ‹type›* (or *Use “‹its name›”*), drawn in this view too, one relationship in both views, or *New ‹type›*, another; Esc draws nothing. Not for a derivation the model does not state. Each an undoable step
21. **Between elements no loaded language relates** — an element of one metamodel and an element of another (an ArchiMate application component and an ATAM risk), or two of a metamodel that defines no relationship types — connect, change type and the "+" menu offer the core's own relationship types: **Association** (`arch:associatedWith`, no direction), then **Depends On** (`arch:dependsOn`, from the element that needs the other to the one it needs), **Has Part** (`arch:hasPart`) and **Refines** (`arch:refines`), each marked *always permitted* and saying why. Where a loaded metamodel permits any relationship between the two, the core's are not offered. They are not listed in the palette. Drawing one writes its triple and its relationship resource as any other. The core notation, loaded with the core, draws each: Association as a solid line with nothing at either end, Depends On as a dashed line with an open arrowhead at the concept depended on, Has Part and Refines as a solid line with an open arrowhead at the target (the part, the concept refined). It lets nesting draw Has Part, the part inside the whole, and Refines, the refining concept inside: a view's reference nested in an element's box may stand for the element having the view as a part or for the view refining the element (Req 3.23), and an element nested in one no loaded language relates it to, for either — Has Part offered first
22. **A link stated only as a triple** — `?option ad:modifiesConcept ?component`, an ArchiMate file of bare `am4:serves`, a process file of `ap:taskOfActivity` — is a relationship once the model opens: for each triple whose predicate a loaded relationship class names as its `arch:unqualifiedForm`, or names the declared inverse of one (`owl:inverseOf`, read the other way, its drawn direction then stated too), between two concepts of the model, that no relationship resource reifies, la-gram makes the resource — the most general class of that form, `arch:source`, `arch:target`, `rdf:reifies` the triple, `arch:inModel`, the qualified predicate from its source — named `relationship/` + the first 20 hex characters of the SHA-256 of "subject predicate object" in the model's namespace, as meta's rules name it (DD-41); one made before, named `relationship-` + the SHA-1, keeps its name. It is listed under Relationships, drawn between its ends where both are placed, and takes properties as any other; opening the file again, in another window or a collaboration room, makes nothing more. A predicate two unrelated classes name is left a triple

### Requirement 5: RDF Export

**User Story:** As an architect, I want to save the model as RDF, so it can live in Git, be loaded into a triplestore, or be read by other Linked Data tools.

#### Acceptance Criteria

1. Export uses prefixed names where possible
2. Prefixes derive from the loaded vocabularies' own `vann:preferredNamespacePrefix`/`Uri` declarations plus the standard ones and `m:` (or the prefix the model declares) for the model's namespace; only prefixes used are written. The model's IRIs are written as prefixed names (`m:model`, `me:…`, `mv:…`, a shape by its view's prefix; criterion 13), and those la-gram minted before DD-41 as before (`m:element-…`, `m:node-…`)
3. Labels are exported as language-tagged `skos:prefLabel`
4. Properties are exported as written (`skos:definition` for descriptions)
5. Relationships are exported in both forms (qualified resource and unqualified triple), with the resource's `rdf:reifies` of the triple — in every format but JSON-LD, which has no triple terms; RDF 1.2 Turtle is read as well as written (a model carrying meta's derivations imports)
6. View geometry is exported as `arch-vis:ArchNode`/`arch-vis:Link` with bounds and routes
7. An **RDF panel** on the right shows the live model as it would be saved — hidden by default, toggled from the toolbar ("{ } RDF") or opened with `?rdf=1`; what it shows — the open **view** (the default: the view, its concepts and its diagram), the **selection** (every concept selected), or the whole **model** (a model too large to show gives its size, with Copy and Download) — remembered per browser; format selector (Turtle default), a "geometry" toggle (the no-geometry profile), counts of what is shown (elements, relationships, views, triples), Copy and Download of what is shown; syntax-highlighted; the selected concept's statements are highlighted and clicking a subject's statements selects it; it does no work while hidden and refreshes debounced while shown; resizable by its left edge (width remembered per browser)
8. Save produces a download (browser) or a file (desktop)
9. Formats: Turtle (default), TriG, JSON-LD, N-Quads, N-Triples, RDF/XML
10. *la-gram:* formats that carry graphs use the Linked.Archi layout (DD-15): `{ns}graph/model`, `{ns}graph/semantic`, `{ns}graph/views`, `{ns}` being the model's namespace `{base}{notation}/{modelId}/`
11. *la-gram:* a "without diagram geometry" profile drops the views graph but keeps views and `arch:inView` membership
12. Only the model is exported — never the metamodel
13. *la-gram:* in Turtle and TriG, an IRI of the model that follows the Linked.Archi IRI layout (DD-41: `{ns}{kind}/{id}`, shapes `{view}#node-{id}` and `{view}#link-{id}`, parts under their owner, joined with `-` after a `#` and with `/` elsewhere) is written with the first of these that applies: a prefix per kind — the model's prefix and `e`, `r`, `v`, `f`, `d`, `doc`, `s` or `g` for `{ns}element/`, `relationship/`, `view/`, `folder/`, `decision/`, `documentation/`, `stakeholder/` and `graph/` (`me:{id}`, `mg:views`) — where the rest is a plain local name; a prefix per view for a shape and its parts, the model's prefix, `v` and the first 8 hex characters of the SHA-256 of the view's IRI (`mv3ef7da72:node-{id}`, `mv3ef7da72:node-{id}-style`), with what a local name cannot hold where it stands escaped (a `/` as `\/`); a reference relative to `@base <{ns}>`; the full IRI. `@base` is written when an IRI is written relative to it, for a namespace that is an `https:` or `http:` IRI ending in `/` with no `#` or `?`. Of two views with one prefix, the view whose IRI sorts first keeps it; a derived prefix that a loaded vocabulary holds for another namespace is not bound. A copy as Turtle is written the same way, and what is written reads back as the same triples

### Requirement 6: SHACL Validation (Client-side)

**User Story:** As a modeler, I want real-time SHACL feedback so I can fix problems as I model.

#### Acceptance Criteria

1. Validation runs against every `shapes` graph of the loaded metamodels (`arch:formalRules`) plus the core and core-vis shapes
2. The data graph is the model plus the `rdfs:subClassOf` axioms and the types of every resource the model references (so `sh:targetClass` on superclasses and `sh:class` on referenced viewpoints/metamodels work)
3. Validation runs after every change, debounced (300 ms); the compiled shapes engine is cached until the metamodels change. It runs off the UI thread (a Web Worker in the browser and the desktop app), so editing never waits for it; a change made while it runs is validated when it ends, and only the latest results are shown. After an edit only the concepts whose results it can change are validated again — the same results as validating the whole model, which is done on opening and when the metamodels change
4. `sh:sparql` constraints (`sh:select`) — which the SHACL library cannot run — run with Oxigraph in the same validation, on the same data and the metamodels' statements they read: their targets, `sh:prefixes`, `sh:message` (a node's name in it where it has one) and `sh:severity` as SHACL defines them; after an edit, for the concepts around what changed. A query Oxigraph refuses is left out, once. Where Oxigraph cannot load, they are not run and the rest is as before
12. **References to what the model does not have** are Violations of the concept that refers: a relationship's end, a view node's element, a link's relationship or end shapes, a shape's view, a route's cells, `arch:inView`, `arch:inModel`, a folder entry — what a file merged as text, edited by hand or written by another tool can leave
5. Each result shows severity, the concept's name and type (a relationship without a name by its ends, an element without one as unnamed), the property as the Properties tab names it, the message and the shape it comes from — a link to the shape's IRI, which opens the metamodel's page for it (a shape written inline, by the named shape it is written in; a check, by the question's IRI); each is set apart from the next, and is reached and shown from the keyboard
6. `sh:message` is shown when present; otherwise a generated message
7. Results are in the Validation tab under the canvas; clicking one shows the concept (switching to a view that contains it). The tab shows the number of Violations, so they are seen while another tab is open; Warnings and Infos are listed but not counted — a view without a viewpoint is a Warning (the published viewpoint shapes declare `sh:severity` on their property shapes). When another model is opened, the last model's findings go at once; the tab says it is validating until the new model's come
8. Violating concepts are marked on the canvas
9. Results match what a server-side SHACL engine reports for the core constraints
10. The Validation tab is scoped, remembered per browser: the **open view** (the default) — the findings on the view itself, the concepts it presents and the nodes and links of its diagram, saying how many more the rest of the model has, with a way to show them — or the whole **model**. With no view open it shows the model. The tab counts the Violations of the scope shown; every violating concept drawn is marked whatever the scope
11. **Model checks** (la-queries Req 10): on request, the Validation tab asks the loaded languages' finding questions and lists their rows beside the SHACL results — the concept, the question as the message, its severity — scoped, counted and marked as they are; it says how many ran, which stopped at their limit, which could not run and why, and when the model has changed since. Another model drops them

### Requirement 9: Model Persistence

**User Story:** As an architect, I want my model to persist, and to navigate its views.

#### Acceptance Criteria

1. The storage model is **Model → Views + Elements + Relationships**; the canvas is a projection
2. A model has a name, `arch:modelConformsToMetamodel` statements, and contains elements, relationships and views (members name it with `arch:inModel`)
3. An element carries its identity independent of any view
4. A relationship likewise
5. A view presents a subset (`arch:inView`) with geometry (`arch-vis:*`); it conforms to a viewpoint (`arch:viewConformsToViewpoint`)
6. The canvas shows one diagram view; changes project back to the model and the view
7. Every resource has a stable IRI, an HTTP(S) URI in the model's namespace
7a. *la-gram:* each model has a namespace, stated on the model as `vann:preferredNamespaceUri` with its prefix as `vann:preferredNamespacePrefix` (`m` by default). New models get `{base}{notation}/{uuid}/` with base `https://example.org/` unless configured (`?base=`), shown and editable when the model is created
7b. *la-gram:* **Model settings** edits the name, namespace and prefix; changing the namespace moves the model's existing IRIs into it (default), each keeping its local part as it is — every one, those inside the triple term a relationship `rdf:reifies` too — or applies only to IRIs minted from then on; a namespace must be an `https:` or `http:` IRI, with no `#` or `?` (a `/` is added at its end), and a prefix must not stand for another namespace; collaborators follow the move
7c. *la-gram:* what is minted follows the Linked.Archi IRI layout (DD-41): an element, a relationship, a view or a folder `{ns}{kind}/{uuid}`; a node or a line in its view's IRI, `{view}#node-{uuid}` and `{view}#link-{uuid}` (flat in the model's namespace, `{ns}node-{uuid}`, in a view whose IRI already holds a `#`); a part under its owner, joined with `-` to an owner whose IRI holds a `#` and with `/` to any other — `{node}-style`, `{node}-style-{hash}` for a presentation context, `{link}-points-{i}` and `{link}-point-{i}`, `{link}-label`, `{node}-label-expression`, `{element}/name/{hash}`, `{element}/picture`. A relationship is minted in its model's namespace. Nothing is renamed: names minted before DD-41 (`{ns}element-{uuid}`, `{node}-style`, `{link}-points-{i}`, `{link}-p{i}`, `{link}-label`, …) and a converter's (`{node}/style`, `{link}/points/{i}`) are a placement's own, matched exactly; a change to its look is written on its own style in place, a moved bend changes only that point's coordinates, a bend added or removed only the route's end, in the route's own names; removed or copied with the placement; and a part replaced — a moved name, a label expression, a name or a picture for a presentation context — keeps its name. A route in another form is written anew under la-gram's names. An imported Exchange file is named as the ArchiMate converter names it: `element/{id}`, `relationship/{id}`, `view/{id}`, `{view}#node-{id}`, `{view}#link-{id}`, the ids encoded as it encodes them; a node or a connection whose id is another's of its kind in the view followed by a part's name (`n1-style` beside `n1`, `c1-point-0` beside `c1`) gets a UUID instead, so that it does not take that part's name
8. Files: Turtle, TriG, JSON-LD, RDF/XML, N-Quads, N-Triples. *la-gram:* *File › Save* (Ctrl/⌘+S) writes TriG, the model in its graphs (`{ns}graph/model`, `semantic`, `views`); *File › Save as ▸* writes any of the six, and Turtle without the diagram geometry
9. Collaborative rooms persist continuously on the server (debounced) as N-Triples plus a Turtle snapshot, and are readable over HTTP (`/rooms/<room>.ttl`)
10. Saving a version is an explicit action: the History tab saves a *checkpoint* of the model's working state with a message (and its author's name: *File › Settings… › You*'s, else the Git account's, else the collaboration name), kept on this machine per model. *la-gram:* it says "checkpoint", not "commit", which means a Git commit (Req 18)
11. Joining a room loads its persisted state
12. The same model always serializes to the same text (deterministic ordering), on any machine and whatever order the metamodels were loaded in: its triples in a fixed order, and the prefixes the standard ones first, then the metamodels' in order of their names (`am4:`, `am4mm:`, `am4vp:`), then the model's own
13. Delete from view vs. from model, as Req 3.7
14. Version history: the checkpoints, newest first, with the triples each added and removed; a checkpoint's differences from the one before or from the model now — by element (each concept added, removed or changed: single values old → new, values added and removed, a view's shapes placed, removed, moved, resized, rerouted — and who made the change and when, where the later version records an edit of it the earlier does not (Req 9.16); design, *Comparing versions by element*) or as triples added and removed; restore a checkpoint — one undoable step. For a model bound to a file in Git, its commits too (Req 18.23)
15. *la-gram:* models written with retired vocabulary (`arch:partOfModel`, `arch:exposedInView`, `arch:contains`, `arch:conformsToMetamodel`, `arch:viewpoint`, `arch:relSource`/`relTarget`/`relPredicate`, element-level bounds) are migrated on open
16. *la-gram:* **who changed a concept, when, and with which la-gram** is recorded as the model is edited, inside each edit, so that undo takes it back and redo puts it again (meta's DD-27, *What a modeller records of its edits*). The model, its elements, its relationships and its views get `dcterms:created` when made and `dcterms:modified` at each change — a change to a placement, a style, a route or a name is one to its view or element, and every change is one to the model; a value set by hand in the same edit stays — and, in the provenance graph, `prov:wasGeneratedBy` the editing activity that changed it last and `prov:generatedAtTime`. An editing activity is one user's edits in one la-gram, from the first change after the model is opened or saved to the next save: `{ns}provenance/edit-{uuid}`, a `prov:Activity` with `prov:startedAtTime`, `prov:endedAtTime` and `prov:wasAssociatedWith` la-gram at its version — `https://app.linked.archi/la-gram/v{version}`, a `prov:SoftwareAgent` and `schema:SoftwareApplication` with `schema:name` and `schema:softwareVersion` — and the user, `{ns}provenance/user-{digest}` of their Git account's page, else of their email address, lower-cased, else of their name: a `prov:Person` with `schema:name` (*File › Settings… › You*'s, else the Git account's, else the collaboration name), `schema:email` (*You*'s) and, unless *Record my Git account with my edits* is unticked, `schema:sameAs` the account's page and `schema:alternateName` its username (Req 18.29); none when nothing is known. What is known of the user when an activity starts replaces what the model had of them. The word before the id is for a reader; the id is opaque, and carries nothing personal. An activity no concept names any more is removed in the edit that leaves it unnamed, and so is a user or a la-gram version no activity names. Not recorded: opening, importing, a new model, undo and redo, merging, pulling, restoring a version, a namespace move, a collaborator's changes. Saved in `{ns}graph/provenance` with every other `prov:` statement and what a PROV class types (Req 5); never offered or edited in the property panel, which shows it read-only (*Last changed*, Req 11.4); left out by the RDF panel's *provenance* switch and of what the diff by element counts as changed, which says instead who made each change and when (Req 9.14), as a merge request's description does; a merge takes the later time, and the activity that ended later, never a conflict (Req 18). The web build writes the page of its version, `v{version}/index.html`, and a release's deploy keeps every earlier version's

### Requirement 10: Model Tree & Navigation

**User Story:** As an architect, I want the whole model in a tree so I can navigate views and find concepts.

#### Acceptance Criteria

1. The model tree is the left column, full height
2. Model → Views + Elements (grouped by type) + Relationships (grouped by type) + Unclassified — for a model with folders of its own, with those folders in the three groups (10.10)
3. The open view is highlighted; concepts placed in it are marked
4. Double-click opens a view; single click selects
5. Right-click menus:
   - **Model**: Rename, Model settings (name, namespace, prefix — also on double-click), New diagram / catalog / matrix
   - **Group** (Views, Elements, Relationships): Views: New diagram view, New catalog view, New matrix view; Elements: New element… (10.16); then New folder… (10.13)
   - **Folder**: a folder of views: New diagram view, New catalog view, New matrix view; of elements: New element… (10.16); then New folder…, Rename…, Move to folder…, Delete folder (keeps its contents) (10.13–10.14)
   - **Element type** (a type's row in Elements): New ‹type›… (10.16)
   - **View**: Open, Select on canvas (while the open diagram holds a reference to it: Req 3.23), Reference in the open view (while another view, a diagram, is open: Req 3.23), Rename, Set viewpoint, Duplicate, Move to folder… (once the model has folders, 10.14), Delete (concepts stay)
   - **Element**: Select on canvas / Add to current view, Rename, Move to folder… (likewise), Delete from model
   - **Relationship**: Select on canvas / Add to current view, Show source, Show target, Rename, Move to folder… (likewise), Delete from model
   - **One of several selected** of a group: *Move N … to folder…* alone (10.14)
6. Selecting on the canvas reveals the concept in the tree
7. Every concept is in the tree regardless of the open view; dragging one onto the canvas places it (and draws its relationships to what is already placed)
8. Views are created (with a viewpoint), renamed and deleted from the tree or the toolbar. ### Requirement 18: Git Storage (la-gram, optional module)

**User Story:** As an architect, I want to open a model from a Git repository and save it back as a commit — given the repository's link and an access token — so that the model is versioned and reviewed where the rest of the architecture lives.

#### Acceptance Criteria

1. Git storage is a module that can be switched off. Off, la-gram shows nothing of it, loads none of its code, sends nothing to a Git host and reads no stored token. It is switched in the build (`LA_GRAM_GIT=off` leaves it out of the bundle altogether) and, in a build that has it, by a setting on this machine — on by default, *File › Settings…* — which `?git=off` overrides for the session
2. A repository is given by its link as copied from the browser — `https://github.com/org/repo`, `https://gitlab.com/group/subgroup/repo`, a GitHub Enterprise or self-managed GitLab address — optionally naming a branch and a file in it (`…/blob/main/models/shop.ttl`, `…/-/blob/main/models/shop.ttl`). The host decides the provider: GitHub and GitLab first; others (Gitea, Bitbucket, Azure DevOps) later, behind the same interface
3. The module talks to the host's REST API over HTTPS — no Git client, no clone, no proxy — so the web and desktop builds behave alike. A self-hosted server that refuses cross-origin requests works in the desktop build only, and the web build says so
4. Access is by a token the user gives: on GitHub a fine-grained personal access token with *Contents: read and write* on the repository (read to open only) — and *Pull requests: read and write* to open pull requests (criterion 22) — on GitLab a personal, project or group access token with `api` (`read_repository` to open only). A public repository opens without one
5. The token is a secret. It is sent only to the host it was given for, and never written into the model, a saved file, the URL, the collaboration room, the log or an error message. The desktop build keeps it encrypted with the operating system's keychain, in the main process; the web build keeps it for the session, or in this browser when the user asks it to. A token can be forgotten
6. **Save to Git** commits the model as one file — in a format of Req 9.8, which the path's extension decides, Turtle by default, and deterministic (Req 9.12), so the commit's diff is the change — to a branch and path (`models/<model name>.ttl` by default) with a message (`Update <model name>` by default); creating the file when it is not there. It may commit to a new branch, started from the chosen one. The commit is the token's account's
7. A save never overwrites a change it has not seen: the commit names the version of the file it replaces (the one opened, or saved last); when the file has moved on, nothing is written, and the user chooses — for the file the model is bound to, first, *Merge with the newer version* (criterion 18); or open the newer version, save to a new branch, or overwrite
8. After a save or an open the model is bound to that file: the next save commits there without asking again for repository, branch and path. The binding — host, repository, branch, path, the file's version and the commit it is at — is kept per model on this machine, as version history is (Req 9.10), not in the model. A commit leaves the model clean (no unsaved changes)
9. **Open from Git**: a link to a file opens it; a link to a repository, or a branch, lists the model files in it (Req 9.8's extensions) to choose one. It opens as Open does — declared metamodels loaded, retired vocabulary migrated (Req 9.15) — and binds the model. `?git=<link>` opens one at startup
10. Failures are said in words: a wrong or expired token, no access, no such repository, branch or file, the file changed (criterion 7), a rate limit, a file too large, the network or a cross-origin refusal
11. In a collaboration room, opening from Git replaces the room's model, asking first as Open does; saving commits what the room holds; the token and the binding stay with the user who saves
12. Checkpoints saved in the History tab (Req 9.10) stay on this machine: a Git save is one commit of the model as it is, not a push of them
13. *Configured by the deployment* (Req 19): the Git hosts la-gram may talk to — each with its kind (GitHub or GitLab) and API address. When the list is given, an address on any other host is refused and no token is sent there; a listed self-hosted host needs no choice of kind. Without the list, any host, as before
14. *Configured by the deployment*: whether a token may be remembered — `ask` (the checkbox is offered; the default) or `never` (every token is kept for the session only, on the web and the desktop alike); and a default repository and folder for new saves
15. *Personal settings* (Req 19): a default repository, branch and folder for new saves, the commit message (a template: `{action}` Add or Update, `{model}`, `{path}`, `{branch}`; `{action} {model}` by default), the prefix of a new branch's suggested name (`la-gram/` by default), and whether the token checkbox starts ticked. A personal setting wins over the deployment's default, never over its policy (criteria 13–14)
16. The kind chosen for a self-hosted host not in the deployment's list is remembered for that host on this machine, and offered next time
17. No token is ever configured: a configuration that holds one is refused
18. **Merge with the newer version**: the model, the file at the commit it was opened or last saved at, and the file at the branch's head are merged three-way, triple by triple (design, *Merging versions*). With nothing changed on both sides, the merged model replaces the model — one undoable step — and is committed to the same branch, naming the head's version; merged again when the branch moves on meanwhile. Otherwise nothing is committed: the merged model replaces the model, holding the version before either change wherever two changes met, the model is bound to the head, and the conflicts are listed (criterion 19)
19. A **Conflicts** tab lists what a merge left to choose — a value, a relationship's ends or a concept's type set differently on each side; a node's bounds or a line's route changed on both; the same element placed on a diagram by both (both placements kept until one is chosen, with *Keep only mine* / *Keep only theirs*); a concept deleted on one side and changed or referred to on the other; a count limit the combination breaks — each named as the model tree names it, with each side's version and *Keep mine* / *Take theirs* (*Keep it* / *Delete it* for a deletion). A choice is one undoable step and can be changed; the tab shows how many are left, and goes once the model is committed or another is opened. A save with conflicts not chosen asks first
20. **Update from main…** (bound models): merges another branch — the default one offered first — into the model: its file at the two branches' merge base, at its head, and the model (first merged with its own branch, if that moved on). Committed so that the host counts the other branch as merged: on GitHub a merge commit with both heads as parents; on GitLab, whose API makes commits of one parent only, to a new branch started from the other branch's head, which the model is then bound to. Conflicts are listed as in criterion 19, and the next save records the update
21. A save of a model with blank nodes asks first, once a session: their triples cannot be matched when versions are merged
22. **Open merge request…** (bound models): proposes the bound branch for merging into the default branch — a pull request on GitHub, a merge request on GitLab — titled by the branch's last commit of the file and described by its changes by element since it left the default branch (Markdown, editable); one already open from that branch into that one is named, not opened again; a model on the default branch, a branch with nothing to merge, and changes not saved to Git (asked) are said first. Offered too right after a save that made a new branch, into the branch it started from (the default branch, for *Update from main* on GitLab). A token without the permission is told which it needs
23. **The History tab's Git history** (bound models): the bound file's commits on its branch, beside the checkpoints, newest first, a page at a time — each with its author, date and short id linked to the host — read when the tab opens and on *Read again*, never polled; read without a token unless one is kept, and a token asked for only on *Read again*. A commit's changes, by element or as triples, against the commit before it or the model now; *Open this version* makes the model the file at that commit — asking first, one undoable step — and keeps the binding, so the next save names the version it last saw and the conflict choice applies. Bound to another branch than the default, the first entry is the branch against the default since they parted, committed or with the model now. A failure to read is said in the tab; the checkpoints are still shown
24. **Pull from Git** (bound models outside shared rooms): reads the file at the current branch’s pinned head and merges it with the incorporated base and latest local snapshot, without a commit or a new branch. Disjoint changes survive; conflicts use the existing Conflicts tab and must be chosen before another pull. A change is one undoable step; identical content adds none. The binding advances to the incorporated remote version; undo leaves that base in place. Local-file saves do not hide local Git changes, and edits made during reads participate in the merge. Model reload/switch, destination change or module stop discards obsolete results; manual Git menu operations do not overlap. Missing or invalid versions, different model identity and unmatchable blank nodes leave model and base unchanged. A pending cross-branch merge must be committed first. Public reads need no token; private reads use the existing read-access flow. Pull reports its result and refreshes the bound History source. Regular checks and clean-only automatic pull are specified in Req 18.25; automatic commits are specified in Req 18.26
25. **Remote checks and optional automatic pull**: a bound model offers *Check for remote changes* and a Git status tab with destination, local/incoming changes, last successful check, next scheduled check and pause/error reason. Checking alone never changes the model, dirty marker or incorporated binding; unrelated commits and serialization-only differences are not incoming model changes. Personal settings offer checks Off (default), every 1, 2, 5 or 10 minutes, and *Pull automatically when unchanged locally* Off (default) or On. Only scheduled checks may auto-pull, only when that option is enabled and the working snapshot still equals the Git base immediately before applying; local-file saves and edits during reads cannot bypass this condition. Automatic pulls are undoable and never commit. Checks are completion-scheduled, paused when hidden/offline/in a room/with unresolved conflicts or pending branch merges, and invalidate obsolete reads on lifecycle, binding or settings changes. One browser-profile owner checks each destination through a Web Lock; separate operation locks coordinate manual and automatic work. Without lock support, automation pauses and manual actions remain available. Returning performs at most one due check; transient failures back off, respecting available host retry timing. Background reads never prompt; access/parse/policy failures pause until manual retry or settings changes. The tab updates without opening or moving focus. History is not polled; immutable file snapshots are cached and local-status snapshots debounced

26. **Optional auto-commit**: Off by default, with explicit opt-in for a model IRI and full Git destination. Settings name the destination and offer After idle (1/2/5/10 minutes, default 2) or At interval (5/10/15/30 minutes, default 10). Local edits reset idle timing; internal merges and status changes do not. Automatic writes use the existing token, format and message template, never dialogs, overwrite, new branches or review requests. Before each write, reconcile the remote even when regular checks are Off; skip canonical content equal to the incorporated base, independently of local-file saves or undo. Use the expected file version and at most three conflict retries. Conflicts, blank nodes, pending branch merges and manual decisions pause writes; choosing conflicts or changing timing alone does not resume. Pauses persist until explicit Resume or a successful manual Git save. The Git tab provides keyboard-accessible Pause/Resume, next-attempt and last-commit times without taking focus. Checks and commits share destination ownership and short operation locks, lifecycle guards and visible/online/room restrictions. A sent snapshot is immutable; successful binding updates reflect that snapshot, and newer local edits stay dirty. Reloaded or replaced models never receive obsolete write results. Before sending, persist destination, source binding, editor identity and a SHA-256 fingerprint without model text or credentials. An uncertain response requires remote confirmation, bounded to one history page when needed, before further automatic writes; unresolved results remain durably recorded and paused. A successful manual Git save acknowledges them. Missing coordination or durable journal storage prevents automatic writes. The same settings and controller serve web and desktop; no settings or status enter model RDF or rooms
27. **A bound model moved to another namespace** (Model settings, Req 9.7b, with its IRIs moved): asked first, in *Model saved to Git*, naming the repository, branch and file — *Move*, or *Cancel* to leave it. The binding follows the model to its new IRI, also when a collaborator moved it or a merge followed a move made elsewhere (Req 18.28); until a commit from here writes the moved model, Pull and the checks accept the file holding the model under its former IRI. *Save to Git* commits the move to the same file, naming the version it replaces. Auto-commit is off for the moved model until turned on again
28. **Merging a model moved to another namespace** (DD-41): when one version has the model under another IRI than the common one, Req 18.18's merge first moves the common version and the other side after it — each IRI in the old namespace to the new one with the rest of its name as it is, inside triple terms too, the model to its new IRI, its `vann:preferredNamespaceUri` the mover's; an IRI the mover still has, a vocabulary's term, stays — then merges. Moved alike on both sides, the common version is moved. A namespace set without moving the IRIs is merged as the statement it is. In la-gram (*Pull from Git*, *Merge with the newer version*, *Update from main…*), when the other version moved the model — its IRI another than the common version's, `{namespace}model` in another namespace — the open model follows it: the merged model replaces it as one change, its session, its binding (Req 18.27; until a commit from here, noting the IRI the bound file still has it under) and the History tab go to the new IRI, the canvas opens the same view under it, and a message says so; undo does not take the move back, and auto-commit is off for the moved model until turned on again. Automatic checks and auto-commit (Req 18.25–18.26) do not follow it: they stop, saying that *Pull from Git* does. A version that holds another model — another IRI in the same namespace, or one not named `{namespace}model` — is not merged, and neither is one where both sides moved it, to two namespaces: either stops before anything changes, saying what to do instead. *Open this version* of a commit that has the model under another IRI asks a second time (*Open and move*) and then moves the open model there with it
29. **Who commits, and whose account.** *Save to Git*, *Save to Git as…*, *Update from main…* and auto-commit write their commits by the user from *File › Settings… › You* — the name (else the Git account's, else the collaboration name) and the address — where a name is known; GitHub takes an author only with both. The token's owner is the committer, and the author where none is known. With a token for a host, la-gram reads once a session the account it acts for (GitLab `GET /user`: `web_url`, `username`, `name`, `public_email`; GitHub `GET /user`: `html_url`, `login`, `name`, `email`) and keeps it on this machine, with the personal settings; a token that may not read it leaves it unknown, and nothing fails. The account of the open model's host — else the one read last — is shown in *Settings › You* (*Git account*, read-only), stands in for a name not given, and is recorded with the edits (Req 9.16) unless *Record my Git account with my edits* (ticked by default) is unticked
30. **Where the model is kept, in Model settings.** With Git storage on, *Model settings* (Req 9.7b) ends with a *Git* part, after the name and namespace: *Address* — the bound file on its branch as the host's page addresses it (`{repository page}/blob/{branch}/{path}` on GitHub, `{repository page}/-/blob/{branch}/{path}` on GitLab, each segment escaped), which *Open from Git…* reads back as the same file; its hint names the repository, the branch, the file and the incorporated commit — or *Not in Git* for a model not bound — and *Your Git account*, as *Settings › You* shows it (Req 18.29), its hint saying whether it is recorded with the edits. Both are read-only: their text can be selected and copied, not changed, and *Apply* leaves them as they are. A module gives them (`MountedUi.addModelSettingsInfo`), asked each time the dialog opens; stopped, the part is gone. *Settings › You*'s *Git account* is read-only in the same way

### Requirement 20: la-gram-git — models in Git, on the command line and in CI (la-gram)

**User Story:** As an architecture team keeping models in Git, I want what la-gram knows of a model to hold where la-gram is not — in a merge request's CI, and for those who merge with `git` — so that a broken model cannot reach the main branch however it was changed, and reviewers see a change by element.

#### Acceptance Criteria

1. A command-line tool, `la-gram-git` (npm package `@linked-archi/la-gram-git`, and a container image), built from la-gram's own source and engine, with the metamodels la-gram bundles; Node 20 or later. What it says of a model file is what la-gram would: each file opened in an engine of its own, as File › Open opens it
2. **check** [paths]: every model file (a model extension and an `arch:Model`; other RDF files are left alone unless named) parses; is exactly as la-gram writes it — its triples written as Save writes them, nothing added; refers to nothing it lacks (Req 6.12); and breaks no shape (Req 6). With `--base <branch>`, a Violation fails only when the change adds it — the file where the branch left `<branch>` is checked too; parsing, the written form and missing references fail always. The shapes' SPARQL-based rules are reported, not failed, for now. Warnings and Info are counted. Each finding listed names its shape's IRI, as Req 6.5 links it. `--shapes <folder>` adds a repository's or an organisation's own shapes: each file a shapes document naming its graph (`owl:Ontology` or `skos:ConceptScheme`), one that does not parse or names none refused by name before any check (exit 2). Exit 1 when a file fails; in GitHub Actions each failure is also an annotation. Reported, never failed, under *IRI layout (DD-41), advisory*: the file's IRIs against the layout every Linked.Archi tool mints — a namespace the model does not state, or not an `https:` or `http:` IRI ending in `/` with no `#` or `?`; then, counted with their first three names relative to the namespace, IRIs holding a character a path segment cannot, with more than one `#`, shapes not named `{view}#node-{id}` or `{view}#link-{id}` for the view their `arch-vis:view` names, parts not named under their one owner (`{owner}-…` to an owner whose IRI holds a `#`, `{owner}/…` to any other), and other names that are not `model`, `graph/…` or `{kind}/{id}`; names given before the layout (`{kind}-{id}`, a part joined to its owner the other way, a converter's `{ns}view/{v}/node/{id}`, meta's derivation rules' `{ns}derivation-{sha1}` and `{ns}derivation-activity-{sha1}[-association]`) counted as legacy. Read from the file's own triples; none of these lines for a model la-gram makes
3. **fix** [paths]: rewrites model files exactly as la-gram writes them, changing no triple
4. **diff** `<branch>` [paths]: the change's model files compared by element (Req 9.14's diff) since the branch left `<branch>`, as Markdown; with `--comment`, posted on the pull or merge request the CI job runs for — or la-gram-git's earlier comment there updated. On GitHub with the workflow's token; on GitLab with a project or group access token in the masked variable `LA_GRAM_GIT_TOKEN` (the job token cannot comment), else the diff is in the job's log. A comment that cannot be made does not fail the job
5. **merge** `%O %A %B %P`: Git's merge driver, with Req 18.18's merge; the result written as la-gram writes it; exit 1 with conflicts, the file holding the version before either change where they met — never conflict markers — and the conflicts listed in words. A move of the model to another namespace on either side is followed as Req 18.28 says, and said on the standard error; moved to two namespaces, the file is not merged: left as ours, exit 1. A file that is not a la-gram model on both sides (an ontology, a shapes file: `.gitattributes` routes by extension), or does not parse, is merged as Git merges text without the driver
6. **init** github | gitlab | merge-driver: writes the CI template for GitHub Actions or GitLab CI (beside an existing `.gitlab-ci.yml`, to include), or routes the model files to the merge driver (`.gitattributes`) and defines it in the clone's Git configuration. Nothing is overwritten
7. The templates are files in la-gram's repository (`ci/`), shipped in the package; they check a pull or merge request against the branch it goes into and comment with its diff
8. Tokens as Req 18.5: read from the CI's environment, sent only to the host's API in a header, never written or shown
9. Released from la-gram's own GitLab pipeline, on a tag `la-gram-git-v<version>` that must match the package's version — the pipeline also runs for merge requests and the default branch, publishing nothing, and for no other tag or branch: la-gram's tests, then the package built, packed, installed from the packed file and run on a model; then, from that one packed file, the npm package — by trusted publishing once the package exists, with provenance; a token only for the first publish — and the image `la-gram-git` in the project's container registry, for `linux/amd64` and `linux/arm64`, each built and tried on its own platform, tagged with the version, its major version and `latest` (a pre-release: npm's `next`, and only its own image tag). Licensed Apache-2.0 as la-gram is
10. Documented: the package and every command (its README, as npm shows it); the CI templates and their setup — the token, a pinned version, own shapes, the image as a GitLab or GitHub Actions job's image (`ci/README.md`); the image — tags, platform, local use with a mounted repository, the variables a `docker run` in CI must pass, copying it into an organisation's registry; and, for administrators of a self-managed GitLab, the merge driver on Gitaly — an option, never a requirement

### Requirement 21: Automatic Layout (la-gram)

**User Story:** As a modeller, I want la-gram to lay a diagram out for me — a model that arrives without geometry, a view made from a question's answer, a diagram that has grown untidy — in the layers its relationships lead through and the bands its language draws, so that I start from a readable diagram and keep my own arrangement where I have one.

#### Acceptance Criteria

1. A diagram's elements are laid out by ELK's layered layout (`elkjs`, in a worker), in a direction — **Down**, Right, Up, Left — the way the relationships lead from source to target; relationships routed at right angles — up to 500 placements by la-gram's router, as *Arrange relationships* routes them (Req 22.2), above by ELK; each element at its current size, or its notation's default size for one not yet placed
2. A nested element is laid out inside its parent, below the parent's name, and the parent sized to hold what is inside it; a relationship the nesting stands for is shown by the nesting, not routed
3. A relationship ending on another relationship is not laid out: its line docks to the other's line, as it does when drawn
4. With bands, elements are kept in ordered bands along the direction — the groups the metamodel's manifest names with `arch:diagramGroupOrder`, first band first (ArchiMate 4.0: Motivation, Strategy, Business, Application, Technology, Implementation and Migration; 3.2: the Motivation aspect, then the Strategy, Business, Application, Technology — its physical elements included — and Implementation and Migration layers); a subtype in its supertype's band; an element of no band (ArchiMate 4.0's Common Domain, a grouping) in the band most of what it holds is in, else most of what it is related to, the upper on a tie. A metamodel naming no order (Basic) has no bands
5. Association does not decide which of its ends comes first; the other relationships do
6. The same diagram laid out twice with the same choices gives the same geometry, to the unit: elements and relationships are given to ELK in a fixed order (band, type, name, IRI; relationships by IRI) with a fixed seed, and positions are rounded
7. Spacing: Compact (30 px between elements, 50 px between layers), **Normal** (50, 80), Roomy (80, 120)
8. Above 2 000 elements, or when ELK fails or takes more than 10 s, the elements are placed in the grid instead, and la-gram says why ("too many elements for the layered layout: placed in a grid"); nothing is half-written
9. **A model opened with no geometry** — no view has any — is laid out so on its first diagram, with the choices last made in *Arrange view*, as part of opening it (not a step to undo); the message counts the elements laid out, and says why when the grid stays. An ArchiMate Exchange import without diagrams the same
10. ***Render as new view*** lays its elements out so, with their routes, with the choices last made in *Arrange view*; from the Graph tab, as drawn when the graph has placed every element
11. ***Arrange view…*** — the canvas toolbar (an icon: three boxes in two rows joined by right-angled lines), the empty canvas's right-click menu — lays out the open diagram or, with elements selected and *Arrange* left at its default, those selected with what is nested in them, kept at their top-left; asks *Direction*, *Spacing* and, when a loaded metamodel orders bands, *Group by band* (**on**), remembered in the browser (`la-gram:arrange-view`); one undoable step, one change for collaborators; and says what it did ("Arranged 8 elements and 8 relationships.")
12. Elements outside the view's viewpoint are laid out with the rest
13. The layout runs off the main thread, in the browser and the desktop app, and la-gram responds while it runs. ELK's effort follows the diagram's size, so that it stays inside the time limit: the given order kept within each layer up to 150 elements; above, banded layers made by longest path; above 500, crossings minimised with less effort. Checked by `npm run bench -- --layout` — diagrams of 100, 500 and 2 000 elements, each with twice as many relationships, laid out by ELK with nothing over anything, the run failing otherwise

### Requirement 22: Align, Size and Route (la-gram)

**User Story:** As a modeller, I want to tidy a diagram without laying it out again — the lines routed afresh where the elements are, elements lined up, spaced evenly, put on a grid, made the same size — with a click for what I do often and a dialog where there is a choice, so that a diagram I have arranged by hand stays mine.

#### Acceptance Criteria

1. Two ways in: a menu beside *Arrange view* in the canvas toolbar, and the empty canvas's right-click menu, open *Arrange view…*, *Arrange relationships…*, *Align to grid…* and *Sizes…*; and quick actions, buttons in the canvas toolbar that act at once — align left, centre, right, top, middle, bottom; distribute horizontally, vertically; match width, height, size; default size; align to grid; arrange relationships. A quick action that needs a selection is disabled until there is one big enough: align and match two or more placements, distribute three or more
2. ***Arrange relationships*** routes the lines of the selected placements — or of the whole view, nothing selected or *Arrange* set so — again at right angles, around the elements and figures in their way, keeping a margin; the placements stay where they are. A line has as few bends as the elements in its way allow; it docks at the middle of a side, or — between placements whose facing sides overlap — at a point the two share, so that it runs straight: the middle of the smaller placement's side, and never outside the middle half of it; where it bends, it bends clear of its own placements, in the middle of the gap it runs through; and it is made longer to cross fewer lines already routed, though not given another bend for one or two crossings. The lines on one side of a placement dock so that none crosses another as it leaves: a line that turns docks where its turn crosses no line running straight on further than it — beside one that ends before it turns — and of the lines turning one way, the one turning soonest outermost; each as near the middle as that allows, 12 px apart or, where the room is short, down to 4. Avoiding a crossing comes before docking at the middle, and no two lines dock at one point and leave along each other. Lines sharing a gap run side by side about its middle in the same order — by which way, and how soon, each turns off — and neither adds a bend. A line between placements that overlap, or one of which holds the other, keeps its route. The same diagram routes the same; la-gram says how many lines it routed, or that they are routed so already
3. ***Align*** moves the selected placements' left edges to the leftmost, their centres to the selection's centre, their right edges to the rightmost — and top, middle, bottom likewise. ***Distribute*** makes the gaps between neighbours equal along the axis, the first and the last staying where they are; where the placements are longer together than the room between the outer ones, their centres are spaced equally
4. ***Align to grid*** moves each placement's top-left corner to the nearest grid line: **20 px**, 10 or 40; across and down (**both**), across only (x), down only (y) — the selected placements, or the whole view. What is in a container is aligned from where moving the container put it
5. ***Sizes*** makes the selected placements' widths, heights or **both** the **largest**'s, the smallest's or the median (of an even number, the mean of the middle two); or each its default size — an element its type's (`arch-vis:defaultWidth` / `defaultHeight`, else 120 × 55), a figure its kind's — the selected, or every placement of the view when none is. Each keeps its centre; a container is never made smaller than what it holds, with its padding
6. Each is one step to undo, and written to the view as a move, a resize or a bent line is: moved and resized placements keep their lines' bends and re-dock their ends; a container grows to hold what is moved into its edge
7. What is moved or resized is what is selected less what is in a selected container, which moves with it; a placement another collaborator holds is left as it is
8. The quick actions use the dialogs' last choices: match to what *Sizes…* last chose (the largest at first), align to *Align to grid…*'s grid and axis (20 px, both, at first) — remembered per browser, and named in the buttons' tooltips
