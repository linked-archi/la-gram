## Known limitations

1. **One placement per element per view.** ArchiMate allows an element to appear twice in a diagram; the canvas keys shapes by element IRI. Exchange imports skip the second placement and count it.
2. **Visual groups and label nodes** — nodes that stand for no element (`arch-vis:ContainerNode`, an Exchange file's `Container` and `Label`) are not drawn, and are skipped on import; elements nested in one are drawn inside the nearest element around it.
3. **Store-led changes are not undoable** from the canvas (a collaborator's edit, an import, a model-level delete started from the tree for a concept not on the canvas). Property-panel edits are, while a view is open: the undo history belongs to the open view and is reset when another opens.
4. **SPARQL constraints** only on a server (Phase 3).
5. ~~**Published shape issue:** `ViewMustDeclareViewpointShape` in the ArchiMate viewpoint shapes puts `sh:severity sh:Warning` on the node shape; SHACL does not propagate it to the property shape, so a view without a viewpoint reports a Violation rather than a Warning. Fix belongs in `linked-archi-meta`.~~ Fixed upstream — the property shapes now declare their own `sh:severity` in both languages (`ViewMustDeclareViewpointShape` / `ViewpointCompletenessShape` in 3.2, `ViewDeclaresViewpointShape` / `ViewpointCompletenessShape` in 4.0), and both bundled copies are re-synced from `linked-archi-meta` (`assets/archimate3/archimate3.2-viewpoint-shapes.ttl`; `assets/archimate4/archimate4-viewpoint-shapes.ttl` on 2026-09-26). A view without a viewpoint reports a Warning. Every other bundled asset matches `linked-archi-meta`.

## Change log

### Not yet committed (2026-09-27) — graph performance, SPARQL tab, views from results

- **Nesting** (Req 3.12, 13.4): an element dropped or moved onto another is drawn inside it — stored as `arch-vis:inNode`, new in core-vis 0.5 — moves with it, and makes it grow to fit (diagram-js `AutoResize`, in the same undo step); the container's name moves to its top. The drop then asks which relationship the nesting stands for, from what the notation says nesting may draw (`arch-vis:nestedEnd`, also new: on ArchiMate's composition, aggregation, assignment, access, realization and specialization notations, and C4's containment and deployment) and the metamodel permits between the two, or None; the one picked is created, not drawn. Junctions hold nothing; a container removed from the view leaves what it held drawn; duplicated views keep their nesting; nested Exchange nodes import nested. In linked-archi-meta: core-vis 0.5 (`inNode`, `nestedEnd`, `RelationshipEnd`), a shape for nesting (one container, on the same view, no cycles), the diagram example nested, and the notations marked.
- **Desktop app** (Phase 5): `npm run package` builds it (`@electron/packager`; only `dist/electron` and `package.json`, in an asar — 8 MB besides the Electron runtime), and `tests/browser/electron.spec.ts` starts the desktop build and checks it loads ArchiMate 4.0 offline. The desktop build had never started: the main bundle is CommonJS but was written as `main.js` in a `"type": "module"` package (now `main.cjs`, the package's `main`); the main build's clean could empty the renderer it shares a directory with; the Electron binary had not been downloaded; and once it ran, the window would not close with unsaved changes — Electron cancels a close the renderer's `beforeunload` objects to without asking, so the main process now asks (Close without saving / Cancel). A new model also counted as unsaved from the start: clearing the canvas's undo history when a view opens was reported as a model change. `electron` moved to the dev dependencies.
- **Version history** (Req 9.10, 9.14; Task 15): a **History** tab under the canvas commits the model with a message — and its author, the collaboration name in a room — and lists the commits, newest first, each with the triples it added and removed; a commit shows those triples with prefixed names, or how the model differs from it now, and **Restore this version** makes it the model as one undoable step (the canvas follows). A commit is a canonical N-Triples snapshot of the default graph (model and geometry), kept per model in IndexedDB — browser and Electron alike — and in memory where there is none. Commits stay on the machine that made them.
- **Property edits undoable** (Req 3.6): an edit, addition or removal in the property panel — and a rename from the model tree — is one step on the open view's undo stack (`DiagramCanvas.recordChange`, a recorded `rdf.store.edit` command); undo and redo redraw the canvas from the store, so a name edited in the panel comes back on the shape. Two faults fixed on the way: in the app the edit went through the App's `property-edited` handler, which wrote every value as plain text — a value chosen from an `sh:in` list (an IRI) or a ticked boolean became a string — and removed every value of the property, so editing the English name dropped the German one. The edit now replaces only the value edited, as the term it is.
- **Choices labelled from reference data** (Req 1.12, 3.6): a metamodel's reference data (`arch:referenceData`) is loaded rather than skipped — bundled for both ArchiMate versions, fetched for the others — and an `sh:in` choice in the property panel shows its name there (`skos:prefLabel`: "Serverless Function"), else its local name in words as before ("Serverless Func"). The palette is unaffected: classification axes come only from the schemes the manifest names for classification.
- **Junctions** (Req 2.18): a shape too small to hold one line of its label — a junction — draws no badge and puts its name under it, as wide as an element; an unnamed one draws none, rather than its type or its IRI in words under every dot (the canvas now knows whether a label is the element's own name: `hasLabel`, `ConceptDescription.named`). Renaming one types under it. In linked-archi-meta, the ArchiMate 4.0 notation had no descriptor for `am4:AndJunction` and `am4:OrJunction` (drawn as plain boxes) and now has both — a filled and a hollow 15 px circle, with pictures — and the 3.2 junctions are 15 px too (were 120 × 55), without a badge.
- **Viewpoints include subclasses** (Req 2.8): a viewpoint naming a class offers its subclasses in the palette and keeps them un-greyed on the canvas (`ViewpointManager.getPermittedTypes`, and `filterByViewpoint` alike), as the published viewpoint conformance shapes already read it (`rdf:type/rdfs:subClassOf*`). The ArchiMate 4.0, C4 and EDGY catalogues gain nothing — 4.0 has no subclasses under the classes its viewpoints name, and the C4 viewpoints list each subclass; in ArchiMate 3.2, 12 viewpoints do (a viewpoint naming Node offers Device, System Software, Equipment and Facility, which the 3.2 ontology makes its subclasses; Business Object brings Contract, Requirement brings Constraint). A class an extension adds under an element appears wherever that element does.
- **ArchiMate 4.0 principles in CI** (linked-archi-meta): a new `archimate4-principles` preset runs the 22 principle shapes over `examples/archimate4-principles-example.ttl`, a model that breaks each principle once, with near misses that must not be reported. The principles only warn or inform, and RDF4J fails on any result, so `ShaclValidator` takes `--expect=<file>` and passes when the results are exactly those listed (`archimate4-principles-example.expected.tsv`); a principle that stops firing, or fires on something new, turns CI red. pyshacl agrees with RDF4J on the example. - **ArchiMate shapes as published** (Req 2.18): new core-vis shape types — `BandedRectangle`, `DoubleBandedRectangle`, `TabbedRectangle`, `Box3D`, `WavyRectangle`, `WavyBandedRectangle`, `Cloud`, `Folder`, `Cylinder` — and `arch-vis:borderStyle`, in linked-archi-meta with their geometry in the vocabulary; the ArchiMate 4.0 and 3.2 notations use them (objects banded, contract double-banded, product tabbed, device/equipment/facility/plateau as 3D boxes, deliverable/gap wavy, representation wavy and banded, meaning a cloud, grouping a dashed folder; location and resource square-cornered, as their pictures). The canvas draws them, docks against their outlines and lays the badge and label out inside the inner lines.
- **Relationship ends from the published markers** (Req 2.17): the canvas draws each decoration from its `arch-vis:decorSymbol` SVG (bundled under `assets/core-vis/markers/`), sanitised and placed by the convention now written into the vocabulary; built-in geometry only as a fallback. Asset fetches revalidate (`cache: 'no-cache'`), so a re-synced snapshot or a new publication is not hidden by the browser cache.
- **Change an element's type** (Req 3.11): from the property panel's type field (a choice of the loaded element types, grouped as in the palette — also for elements not in the view) or the right-click menu's "Change type…" (searchable); same IRI, name, properties and placements; the default name follows; relationships not permitted with the new type named before, kept after; undoable on the canvas.
- **Right-click menu** (Req 11.9): on elements and relationships — Rename, Change type…, Append…; Properties, Show in model tree, Show relationship graph; Copy IRI; Delete from view, Delete from model…
- **Rename on the canvas** (Req 3.3): double-click an element's box (or F2) and type its name — Enter keeps, Esc drops, undo/redo restore; the name in the shown language, never empty. `diagram-js-direct-editing` (MIT, bpmn-io) is a new dependency.
- **Linked.Archi Core** (Req 1.12): the core ontology as a metamodel, first in the Metamodels menu — a generic **Element** (palette group "Generic") and a generic **Relationship**, alone or alongside a language, whose grouping stays the default. Bundled manifest and classification (`assets/core/core-metamodel.ttl`, `core-tax.ttl`) until meta.linked.archi publishes them; the palette and the relationship manager offer a core class only when the core's own classification names it. The generic relationship ranks last and never makes an append ambiguous.

- **Graph query, fast** (Req 17.6): the generated query is reshaped for Oxigraph — a property path for the two directions, a filter instead of `BIND`, every hop as `OPTIONAL { … } FILTER(BOUND(?r))` so the optimizer cannot reorder it: 10 ms at depth 5 on 100 elements (was 7 s), 42 ms on 500 (was minutes). Offered as **SELECT** (a table, the default) or **CONSTRUCT**, and *Run in SPARQL tab* runs it.
- **SPARQL tab** (Req 16.2): results as tables — SELECT under its projected columns, CONSTRUCT as subject / predicate / object — with prefixed names that reveal the concept; the long query scrolls in its own box and the results come into sight.
- **Layout** (Req 11.1, 11.4, 11.6–11.7): the model tree hides ("☰ Model" in the toolbar) and resizes by its right edge, like the palette and the RDF panel. The bottom panel maximizes over the workspace (⤢, or double-click the tab strip; ⤡, Esc or folding restores; opening a view restores it) — in the window rather than a separate one (design decision 12); the Graph drawing follows its area's size.
- **About ‹type›** (Req 3.10): a section under the model tree, in the left panel — folds to its header, resizes by its top edge, both remembered — with what the ontology and the taxonomy say about the selected concept's type, or a type picked in the palette — definition, other names, guidance, a relationship's typical ends, a viewpoint's concepts and stakeholders (for a view: its viewpoint), superclasses, changes, the specification link; classification per axis with the group's notes and its other types. Sections fold (remembered); linked types open in place with a way back. In Electron, web links open in the system browser.
- **Build**: the web bundle is named by its content (`bundle.<hash>.js`) — `npm run serve` sends no cache headers, and a plain reload kept running a cached `bundle.js` after a rebuild.
- **Views from results** (Req 16.3, 17.7): *Render as new view* works (it was a button with nothing behind it) for SELECT and CONSTRUCT results, and the Graph tab has **＋ New view**, laid out as drawn.
- **Graph performance** (Req 17.6, 17.8): running the Graph tab's SPARQL CONSTRUCT in Oxigraph took seconds from 100 elements (7 s at depth 5) and grew with the model, so the tab walks the store breadth first instead — milliseconds, growing with what is reached; the query stays the export, and tests require the walk and the query to return the same triples (decision 11).
- **SPARQL tab**: an empty `CONSTRUCT` result with a `#` in a `PREFIX` IRI came back as an empty table — the query-form detection read comments inside IRIs and let the prefix-stripping swallow the query; it now masks IRIs and strings first and takes the first form keyword.
